# Releasing bgtail

bgtail is distributed through the Homebrew tap at
[`PeachlifeAB/homebrew-tap`](https://github.com/PeachlifeAB/homebrew-tap). This
document covers the **producer** side — what bgtail must do before the tap can
pin it. The **consumer** side (writing the formula, building bottles, uploading
to GitHub Releases) is documented once for all formulas in the tap's
[`docs/DEVELOPMENT.md`](../../homebrew-tap/docs/DEVELOPMENT.md); it is not
repeated here.

## Rule zero: never release from remembered state

**Every prior release in this tap that broke did so because state was assumed
rather than read.** The tap's git log is the evidence:

| Commit | What went wrong |
|--------|-----------------|
| `56ed193` | bgtail 0.1.0 was re-tagged; the formula's sha256 still pinned the old tarball |
| `fef14f6` | sive 0.1.2 sha256 was computed against the wrong GitHub-generated tarball |
| `aa7a0bb` | sive 0.1.4 formula pointed at a tag archive instead of the published sdist asset |
| `a8f85d1` | formula used the wrong `depends_on macos:` syntax and shipped before `brew style` caught it |

Re-tagging silently changes a GitHub archive tarball's sha256. A worktree that
looks clean from ten minutes ago may not be. A tag you believe points at `HEAD`
may be several commits behind. None of this is visible from memory — it has to
be read immediately before the release.

So the first step of every release is not a version bump. It is:

```bash
task release:preflight
```

This runs the tap's `bin/preflight bgtail`, which prints the current `git
status`, `git log`, and `git tag` for **both** bgtail and the tap, fetches the
live tarball and compares its sha256 against what the formula pins, and exits
non-zero on any drift. Read its output. Do not skip it because you "just
checked" — the entire failure history above is people who had just checked.

## What preflight enforces

It blocks the release on:

- bgtail's worktree being dirty
- bgtail having unpushed commits
- the tag the formula references not existing, or being behind `HEAD`
- `pyproject.toml`'s version disagreeing with the tag
- the formula's `sha256` not matching the artifact users will actually download
- the formula having no `bottle do` block

It warns (without blocking) on a missing tracking branch, an unpushed tap, or
dynamic versioning that needs a committed `_version.py`.

## Version locations

bgtail's version lives in **four** places that must agree. `uv.lock` was found
holding a stale `2.0.2` while `pyproject.toml` said `0.1.0`, so this is not
theoretical:

| Location | How it is kept in sync |
|----------|------------------------|
| `pyproject.toml` `version` | Source of truth; edited by hand |
| `bgtail/cli.py` `_BASE_VERSION` | Edited by hand; asserted by `tests/test_release_version.py` |
| `uv.lock` | Regenerated by `uv lock` after the bump — commit the result |
| git tag | Created in step 4 below; asserted by `tests/test_release_version.py` |

`tests/test_release_version.py` fails if the CLI's reported version drops the
declared version, and — on a tagged commit — if the tag disagrees with
`pyproject.toml`. That test is what turns a post-release `brew test` failure
into a pre-release `task test` failure.

## Release procedure

### 1. Preflight the current state

```bash
task release:preflight
```

Expect failures if you have uncommitted work. Resolve them before continuing.

### 2. Bump the version

Set the same value in `pyproject.toml` and `bgtail/cli.py` (`_BASE_VERSION`),
then regenerate the lock:

```bash
uv lock
```

### 3. Run the gates

```bash
task test
```

`tests/test_release_version.py` covers version agreement. The full gate set is
`fmt`, `lint`, `typecheck`, and `tests`.

### 4. Commit, tag, and push

The tag must point at the commit you intend to ship, and must be pushed before
the tap can reference it:

```bash
git commit -am "release X.Y.Z"
git tag X.Y.Z
git push origin main --tags
```

bgtail uses **unprefixed** tags (`0.1.0`, not `v0.1.0`). sive uses `v`-prefixed
tags; do not copy its convention.

**If you re-tag for any reason, the tarball sha256 changes.** Re-run preflight
and recompute the hash — this is failure `56ed193`.

### 5. Confirm the tag is live, then hand off

```bash
task release:preflight
```

It will now fail on the sha256 comparison, because the tap still pins the
previous version. That failure is the hand-off signal: it prints the live
sha256 for the new tag. Take that value to the tap and follow
[`docs/DEVELOPMENT.md`](../../homebrew-tap/docs/DEVELOPMENT.md) — update `url`
and `sha256`, build and upload the bottle, add the `bottle do` block, push.

### 6. Verify as a user

```bash
brew update
brew install peachlifeab/tap/bgtail
bgtail --version
brew test peachlifeab/tap/bgtail
```

Re-run `bin/preflight bgtail` from the tap one final time; it should pass
cleanly.

## Known gap: bgtail has no bottle

Preflight blocks on this, per the tap's documented rule that every formula
release ships a bottle. bgtail's formula currently has no `bottle do` block, so
**the first release after adopting this process requires building one**. See
"Building and Releasing a Bottle" in the tap's `DEVELOPMENT.md`.

## Known gap: `--version` always reports `.dev`

`format_version()` in `bgtail/cli.py` unconditionally renders
`bgtail X.Y.Z.dev+d<date>`. In a Homebrew build there is no `.git` directory, so
the date falls back to **build time**, and the installed binary reports a
version derived from when the user compiled it. The formula's
`assert_match "0.1.0"` passes anyway because it is a substring match.

This is cosmetically wrong for a tagged release but does not currently break
installation. Fixing it means giving `format_version()` a release mode; that
work is not part of this process.
